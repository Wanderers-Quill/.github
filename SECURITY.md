# Security Policy

## Supported versions

Wanderers-Quill is in early development. There are no stable releases yet.

| Version | Supported |
| :--- | :--- |
| v0.1 (in development) | Yes, security fixes only |
| < v0.1 | No |

Once v0.1 is released, this table will list supported release lines.

---

## Reporting a vulnerability

**Do not report security vulnerabilities through public GitHub issues.**

Instead, use one of these private channels:

1. **GitHub private vulnerability reporting:** Go to the repository's **Security**
   tab and click **"Report a vulnerability"**. This is the preferred method.
2. **Email:** If you cannot use GitHub, email the maintainer at
   `brooklyndevcontact@disroot.org` with the subject line `[SECURITY] Wanderers-Quill`.

Please include:

- A description of the vulnerability.
- Steps to reproduce it.
- The affected version or commit.
- Any proof-of-concept code or logs.
- Your assessment of the impact.

---

## What to expect

Wanderers-Quill is maintained by a single developer with limited time. We will
do our best to respond promptly, but we cannot promise a fixed SLA.

| Stage | Expectation |
| :--- | :--- |
| Acknowledgment | Within 5 business days |
| Initial assessment | Within 10 business days |
| Fix or mitigation | As soon as reasonably possible, depending on severity |

We will keep you informed of progress and will credit you in the advisory if
you want credit.

---

## Disclosure

We prefer coordinated disclosure. We will work with you to agree on a disclosure
date after a fix is available. We will publish a GitHub Security Advisory when
the fix is released.

Please do not disclose the vulnerability publicly before a fix is available.

---

## Scope

This policy covers the code in the Wanderers-Quill repositories. It does not
cover:

- Vulnerabilities in third-party dependencies (report those to the upstream
  project).
- Issues in a self-hosted instance's configuration (e.g., a weak password).
- Social engineering attacks.

---

## What we ask of you

- Act in good faith.
- Do not exploit the vulnerability beyond what is necessary to demonstrate it.
- Do not access or modify other users' data.
- Give us reasonable time to fix the issue before public disclosure.
